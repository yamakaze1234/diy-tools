# 配置利润检测与后台监控联动实施方案

日期：2026-09-24；需求变更：2026-09-25。工作台一键检测双口径保持原设计；后台提醒目标已改为 ERP 配件单价变化，现行边界见第 12 节。第 7–9 节的后台整机利润通知部分仅保留为旧方案记录。

## 1. 目标与分阶段交付

第一阶段在配置工具增加“一键检测利润”：读取已保存配置，查询最新 ERP 成本，保存可追溯快照，同时检查 ERP 利润和核算利润，显示两种口径的亏损和利润变化及原因。第二阶段让后台监控机器人读取同一套配置业务快照，定时重新采集成本，按同一规则发钉钉提醒。第三阶段再按实际需要整理配置主存储；第一阶段不重构现有同步协议。

默认使用配置工具保存的到手价，不声称是抖店实时活动成交价。抖店价格采集不属于本次实施范围。ERP 仅查询，不写回价格、库存或商品关联。

## 3. 用户操作

在配置总览增加“一键检测利润”。默认当前店铺，可选勾选配置；默认排除已删除配置和空链接草稿。每轮使用点击时已成功保存的配置快照；存在未保存内容时先走现有保存流程，保存失败则不启动检测。

按钮显示准备、采集、计算、完成状态，后台任务执行，重复点击返回当前任务。结果页显示本轮覆盖数、有效数、亏损数、变化数和无法计算数，可按严重程度筛选。

明细字段：店铺、链接、配置、到手价、分期费、ERP 总成本、含税核算总成本；ERP 利润和核算利润分别显示当前利润、上次检测利润、较上次差额、累计比较基准、累计差额、命中原因和有效状态，并显示配置版本与各自成本时间。统计同时提供去重配置数和分口径命中数。展开显示具体配件的价格与数量差异；提供历史查看、重新检测、显式重设变化基准。第一阶段只在工具内展示，不发送钉钉。

检测使用独立成本快照，不自动覆盖编辑器里已确认应用的 ERP 成本。结果说明“本次检测成本”；将成本应用到配置仍走现有 ERP 预览和确认流程。

## 4. 利润口径与规则

两种口径默认都检查，分别应用亏损超过 300 元、利润变化超过 100 元的规则：

- ERP 实际利润 = 到手价 × 98% − Σ(实际配件 ERP 单件成本 × 数量) − 分期费。
- 核算利润 = 到手价 − Σ(实际配件含税核算单价 × 数量) − 到手价 × 4% − 100 元 − 分期费。

ERP 成本取本轮最新只读查询，核算成本取配置工具已保存的含税核算单价（tax），保留其更新时间；核算成本不是 ERP 自动更新的数据。ERP 查询失败不阻止核算利润检测，核算成本缺失也不阻止成本完整的 ERP 利润检测。两种口径分别保存有效历史、变化基准、亏损状态和恢复事件，不能交叉比较或互相移动基准。

分期费和特殊配件处理复用现有业务定义，实施时以 prototype/core.js、actual-parts.js 和当前分期函数为依据。展示配件隐藏与否不影响实际配件成本。

所有金额以整数分保存，计算采用十进制定点及明确舍入规则，与当前配置总览做黄金样例对照。先锁定单价精度、数量精度、98%、到手价的 4% 和固定 100 元的舍入位置及分期舍入方式，再实现；不凭不同语言默认浮点行为计算。

| 规则 | 行为 |
| --- | --- |
| 亏损 | 每种口径独立判断 profit_cents < -30000（利润低于 -300 元）；等于 -300 元不触发 |
| 变化 | 每种口径独立判断 abs(current - anchor) > 10000（变化超过 100 元）；上涨和下跌都显示 |
| 首次检测 | 建立变化基准；已亏损超过 300 元仍显示亏损 |
| 上次差额 | 每轮显示，相对上一份有效检测，辅助理解 |
| 累计变化 | 相对变化基准；未超过阈值不移动基准，防止小幅连续变化漏报 |
| 手动检测基准 | 本轮结果事务成功落库后，命中变化的配置口径以该口径本轮利润建立下一段基准；历史保留原基准及触发差额 |
| 持续亏损 | 结果页每次都显示；机器人仅状态首次进入、进一步变化超阈值、或每日汇总时通知 |
| 恢复 | 从亏损状态到 >= -30000，记录一次恢复事件 |
| 缺成本或失败 | 保留历史有效记录与基准，本轮为不可计算；不回退人工成本冒充 ERP 成本 |

缺失、非有限值、负成本、异常数量、无有效 goods_id、ERP 回退成本均不能产生“有效 ERP 利润”。核算口径要求每个应计成本配件的 tax 完整、有限且非负，数量有效；缺失不能按零累加，缺少 goods_id 本身不阻止核算利润计算。明确返回的合法零成本与缺失不同，需要保留来源；特殊非成本行按已有业务规则处理。不同来源、不同工作区、不同公式版本不能直接比较，建立新基准并说明原因。

配置改价、换配件、改数量均保留同一配置身份并记录版本，不自动丢弃此前基准。成本变化原因按配件逐项解释；换配件采用旧行移除、新行加入计算，金额分解必须与总利润差额一致，舍入差额独立列示。

## 5. 本地数据库设计

第一阶段在 workspace.sqlite 增加独立 profit_* 表，不改变现有 records/outbox/云端合同。新增本地表不自动同步云端，ERP 成本仍留本机。表结构通过独立 schema_version 和事务迁移维护。

| 表 | 主要内容 |
| --- | --- |
| profit_runs | run_id、来源 manual/monitor、状态、起止时间、工作区、配置修订、公式版本、覆盖及失败统计 |
| profit_config_snapshots | run_id + workspace/shop/config 身份、链接、售价分、分期参数及费用、业务 JSON、配置内容哈希 |
| profit_part_snapshots | 配置快照、稳定配件行 ID、goods_id 文本、数量、ERP 单价、含税核算单价（tax）、各自来源/更新时间/质量状态 |
| profit_results | 口径 erp/accounting、本轮利润、上次有效结果 ID、所用基准 ID、两个差额、命中规则、不可计算原因 |
| profit_baselines | 工作区+店铺+配置+口径+来源范围，变化基准和亏损状态，关联结果 ID |
| profit_settings | 阈值、检测范围、导出联动开关和明确的保留策略版本 |

配置快照按 run_id 和配置身份建立唯一约束；profit_results 按 run_id + 配置身份 + 口径建立唯一约束，goods_id 永远存文本；结果与比较基准变更在同一事务提交。配置快照不含图片二进制、账号凭据和无关排版资源。结构化字段供检索，业务 JSON 供复现与兼容，不另造第二份可独立编辑的配置源。

不跨网络查询持有数据库写锁。运行中崩溃的任务重启后标记中断，不算成功检测，不移动基准。默认第一版不自动清理历史，提供记录数/占用统计；未来清理需有明确保留策略和预览。

## 6. 配置工具实现拆分

拟新增 python-desktop/profit_store.py（迁移与事务）、profit_service.py（任务和查询编排）、profit_rules.py（规则与原因分解）、prototype/profit-check-ui.js（结果界面）。文件名在实施前按当前路由组织确定。

service.py 接入任务生命周期，现有本机服务路由增加启动检测、查询进度、获取结果、查询历史及重设基准操作。接口只使用现有本机认证与请求校验方式，不新增公网入口。任务请求包含范围和请求 ID，服务端验证身份与数量上限。

先复用现有只读 SQL 正规化；为按 ID 分批查询增加明确的“局部结果”校验，不能把局部结果误当完整目录替换。部分批次失败只影响依赖该批次的配置，界面明确部分成功；同一轮每个 goods_id 使用唯一采集值。扫描时发生配置编辑，结果仍对应点击快照并标记配置已更新，可再次检测。

## 7. 后台联动合同

第二阶段采用已生成业务快照的本机文件交付，避免机器人必须等待配置工具在线，也避免机器人直接读取或修改工作台业务数据库。它替代此前讨论的仅在线只读接口方案；以后可添加同合同接口。

配置工具增加显式“发布到后台监控”开关和目标目录设置，原子写入 profit-monitor/manifest.json。合同名 profit-monitor/v1，包含 schemaVersion、sourceId、workspaceId、revision、publishedAt、contentHash、公式版本和完整配置列表；每项含店铺/链接/配置身份、业务哈希、售价、分期数据、实际配件 ID、数量、含税核算单价（tax）、核算成本更新时间与完整性状态，明确支持 erp/accounting 两种口径。凭据、图片及 ERP 成本不导出；机器人用自身只读连接采集最新 ERP 成本，核算利润使用最后发布的含税核算单价；配置工具保存核算价变化后自动发布，由机器人重算。

业务保存成功后重新发布；发布失败显示“联动尚未更新”并可重试，不谎报同步成功。旧版合同、哈希错误、重复 ID、超限内容或非完整快照被拒绝，保留最后有效版本并显示异常。完整快照中的停用/删除语义必须明确；只接受带完成标志的原子完整版本，不能因半文件或解析失败停止全部监控。

机器人首次由用户选择 manifest 路径并预览范围。记录来源身份和修订，来源身份改变须重新绑定；仅修订回退保留旧快照并提示，正常删除配置停止后续检测并保留历史。配置工具关闭后仍基于最后发布版本检测，通知标明配置发布时间；文件长期未更新不等同于配置错误，区分“上次成功读文件时间”和“业务内容修改时间”。

机器人本地新增 profit_monitor.sqlite3 保存运行、结果、基准、事件，和工作台的手动检测基准完全独立。复用同一规则合同、版本及黄金测试数据，Python 计算模块在实施中选定可打包的共享方式，禁止两份公式各自演进。两个 EXE 必须能独立启动，不能依赖开发机另一个仓库的绝对路径。

## 8. 后台采集与通知

新增 profit_monitor.py、profit_panel.py，扩展 sql_inventory_source.py 的专用成本查询，避免改变现有库存正规化输出语义。按精确 goods_id 查询公司大库单件成本；超过现有单批 1000 个 ID 时分批，限流并支持取消，与库存任务协调连接和负载。

默认每 120 分钟；配置发布变更合并触发一轮，可暂停和手动检测。上轮未结束不启动第二轮；程序关闭/休眠期间不声称仍在监控，恢复后补一轮最新检测，不补发每个错过时点。

notification_robots.py 增加 profit 通道与用户选定接收者。默认不自动订阅现有所有机器人，开启时展示具体接收者和消息预览；已有密文凭据与发送链路复用，不读取或复制到新合同。

提醒采用持久事件与逐接收者回执。事件创建时固定比较基准和目标接收者，事件 ID 幂等；成功收件人不重复发送，明确失败按既有策略重试，结果未知不盲目重发。检测状态基准与送达回执分离：待发送事件承担累计变化，后续变化可生成关联事件，不能因为发送失败丢掉变化，也不能每轮重建同一事件。新增收件人不补发历史积压。

同轮按店铺合并，亏损优先，同一配置只保留一条配置明细，其下分别列出 ERP 利润和核算利润的结果、变化及命中规则；任一口径命中即提醒，两者同时命中合并发送。事件去重身份包含口径，单个口径恢复不得清除另一个口径的亏损状态。包含当前利润、触发基准、变化金额、成本变化原因、配置发布时间和成本采集时间。持续亏损每日汇总一次，恢复提醒一次；消息超长按稳定分片发送并各自去重。利润异常和采集异常分开分类，采集失败不生成亏损告警。

## 10. 验证与数据保护

规则覆盖：两种口径分别验证 -300/-300.01，±100/±100.01，500→460→420→380 累计下降；首次即亏损；亏损恢复；分期/数量/改价/换件；空 ID、超长 ID、缺成本、合法零成本、成本回退、重复仓库和部分查询失败。

双口径覆盖：ERP 查询失败但核算成本完整、核算成本缺失但 ERP 完整、两者同时命中、只有一方变化/恢复、未绑定 ERP ID 但核算价完整、更新 tax 后联动重算；验证基准互不影响，双口径消息合并且不丢失明细。

持久化覆盖：重复点击、数据库事务失败、运行中退出、保存同时检测、工作区切换、公式升级重建基准；通知覆盖成功、部分成功、明确失败、结果未知、重启与接收者变化。合同覆盖截断、哈希不符、不支持版本、删除项、来源变更和修订回退。

在隔离数据副本执行迁移与测试，实际业务库不用于破坏性测试。升级前使用 SQLite backup API 备份运行中数据库，或正常退出后完整备份 data；不能只复制正在写入的主 sqlite 文件。验证 quick_check、原有配置数量/内容哈希、同步队列和历史未丢失。增量新表不改老表语义；关闭新功能可回退旧程序，保留新检测记录。

UI 验证必须真实点击，不将单元测试或打包成功当作验收。发布包排除业务数据库、ERP 设置、登录缓存和密钥；用户安装目录的数据保留。任务收尾临时文件按回收站规则处理，不清理来源不明的旧文件。
