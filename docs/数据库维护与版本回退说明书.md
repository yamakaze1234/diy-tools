# DIY 配置工作台：数据库维护与版本回退说明书

面向人员：第一次接触数据库的日常维护人员。编写日期：2026-09-20。适用基线：本项目 Python 桌面版 0.3.13、CloudBase 协议 2。

本说明书按本次实际读取的项目代码编写。没有连接正式云数据库，没有检查云端备份是否已开通，也没有执行恢复、升级或回退。文中的维护频率是建议制度，不代表系统已经自动完成。实际运行的 EXE、云端迁移状态和备份可恢复性，维护人员仍需按本文核对。

0.3.14 补充：本版新增共同加购价、跨商品统一保存和多方案展示，不新增数据库表或 SQL 迁移。旧版客户端不能完整理解多选展示规则；使用新功能后，不应未经兼容验证直接回退旧客户端并连接正式工作区。数据路径与备份原则保持一致。

## 1. 先记住这五件事

1. 平时主要做检查、备份、抽查恢复，不需要每天进入数据库改表。
2. 当前默认数据在 EXE 同一文件夹的 `data`。备份要在正常退出程序后复制整个 `data`，并保留配套完整程序包。
3. “恢复昨天的配置”“换回旧软件”“恢复整个云数据库”是三种不同操作，影响范围不同。
4. 同步会把修改传播给其他电脑。发生误删时先停止有关电脑的编辑和同步，再判断恢复范围。
5. 没有经过恢复演练的备份，只能算“已经复制的文件”，不能保证能恢复业务。

## 2. 数据到底放在哪里

### 2.1 三套数据各管什么

| 位置 | 主要作用 | 谁负责维护 | 恢复它不能解决什么 |
| --- | --- | --- | --- |
| 每台电脑的本机 data | 当前业务状态、本机草稿、同步队列、历史版本、图片、本机 ERP 信息 | 工作台维护人员 | 不会自动把云端回到同一时刻 |
| CloudBase PostgreSQL 与云存储 | 已提交的协作数据、成员、同步日志和回执、原始素材 | 云环境管理员与开发人员 | 无法找回从未上传的本机草稿；不等于公司 ERP 备份 |
| 公司 ERP / SQL 数据库 | 公司商品、库存及成本来源 | 公司 ERP 管理员 | 工作台回退不会恢复 ERP 原始账务 |

工作台编辑先保存到本机。默认每两小时做一次云同步；“多人同步 → 立即同步”可马上执行，并重新计算两小时间隔。暂停自动同步后仍可手动同步。首次发布或空白工作区接收数据有单独流程，不能依靠“还没到两小时”来保证隔离。

配置、人工核算价、店铺设置、模板、输出源、机箱图库参与多人同步；ERP 成本、可销数、生成图和 ZIP 留在本机。公司 SQL 的读取、预览、应用与 CloudBase 多人同步是两条流程。

### 2.2 找到正在使用的 data

1. 找到平时启动工作台的快捷方式，右键查看属性中的目标；如果通过启动脚本运行，同时核对脚本指向的程序。
2. 打开实际 EXE 所在文件夹，找到旁边的 `data`，不要凭桌面上文件夹名称猜测。
3. 当前源码默认位置为 `python-desktop/data`，打包版默认为 EXE 旁的 `data`。
4. 若启动环境指定 `DIY_WORKBENCH_DATA_DIR`，则以该路径为准；`DIY_WORKBENCH_USER_DATA` 可另外指定运行缓存位置，维护记录也要登记。Python 版不能照搬旧 Node 文档的 `DATA_DIR` 用法。
5. `data/runtime/desktop-runtime.json` 可帮助核对程序版本、PID 和本机端口；它可能是上次运行遗留文件，不能单凭它判断程序当前还在运行。

第一次启动且新位置没有 data 时，程序可能从 `%APPDATA%/DIYWorkbench/data` 复制旧数据，旧目录保留。不要为了“刷新”而删除 data，否则可能引出旧数据迁移或重新初始化。

### 2.3 data 里的文件怎么理解

| 文件或目录 | 用途 | 维护要点 |
| --- | --- | --- |
| state.json | 本机业务状态文件 | 不是唯一数据来源；仅替换它可能被 SQLite 中的状态覆盖 |
| workspace.sqlite | 同步状态、记录、草稿、冲突、未确认提交、本机修改记录等 | 与 state.json 一起按同一时点保留 |
| versions.sqlite | 本机业务历史快照 | 不是独立的整机备份，不包含原图字节 |
| assets | 本机原始素材缓存 | 单独恢复数据库不保证图片齐全，未缓存的原图需依赖云存储 |
| images | 本机生成的图片文件 | 需要保留既有输出时一起备份 |
| backups 及迁移前 JSON | 特定操作自动留下的备份 | 不代表每日完整备份，也不代表每次升级都会产生完整备份 |
| sql-credentials | 本机加密的 SQL 连接凭据 | 换 Windows 用户或换电脑后可能需要重新输入，不把密码写进交接表 |
| runtime | WebView2 缓存及运行信息等 | 完整备份中保留；测试恢复时不依赖其中的旧登录状态 |
| *.sqlite-wal / *.sqlite-shm | SQLite 运行时的配套文件 | 不单独删除，不从别的时点拼接到数据库旁边 |

SQLite 可以理解为“保存在电脑上的数据库文件”；PostgreSQL 是云端数据库服务。WAL 是数据库的配套写入记录，程序运行时只复制 `.sqlite` 主文件可能漏数据。最适合新手的办法是正常退出工作台，确认进程结束，再复制完整目录。

## 3. 第一次接手：建立一张维护登记表

以下字段逐项填写，不知道的标为“未核实”，不要猜。

| 项目 | 要登记的内容 |
| --- | --- |
| 程序 | 当前版本、实际 EXE 路径、配套完整 ZIP 所在位置 |
| 本机数据 | 每台电脑名称、使用人、实际 data 路径、自定义运行目录 |
| 云环境 | 腾讯云账号归属、地域、环境名称、环境 ID |
| 工作区 | workspaceId、业务归属；它与环境 ID 不是一个值 |
| 云服务 | workbenchApi 云函数版本或代码哈希、配置版本、已执行迁移清单 |
| 人员 | 日常维护人、云环境管理员、开发联系人、ERP 管理员 |
| 本机备份 | 存放位置、频率、保留期限、最近验证日期 |
| 云端备份 | 是否可用、备份范围、成功时间、保留期限、能否恢复到新环境 |
| 素材与账号 | 原始素材备份方式、成员与认证账号恢复方式 |
| 业务要求 | 最多能接受丢失多久的数据、最多能停用多久 |

“最多丢失多久”例如一天；“最多停用多久”例如两小时。这是业务负责人要定的目标，不是当前系统承诺。若一天只能接受损失一小时的数据，每天一份备份就不够，需要增加频率并验证云端能力。

## 4. 日常维护怎么做

### 4.1 每天：约 5～10 分钟，不含备份耗时

1. 打开工作台，核对账号、成员和店铺，抽查两三套常用配置及图片能否打开。
2. 打开“多人同步”，检查待上传数量、冲突、错误和最近同步结果。未到同步周期的待上传不一定是故障；持续不减少或出现错误才要追查。
3. 需要完成当天交接时，先正常保存，再“立即同步”；确认结果。如果有冲突或结果待确认，保留原队列并登记，不以清空队列代替处理。
4. 查看公司库存更新时间；库存陈旧时走公司 SQL 的读取和预览流程。云同步成功不能证明库存已经刷新。
5. 正常退出程序，完成当天完整本机备份。云同步失败也要备份，因为草稿可能只在本机。
6. 记录备份路径、时间、程序版本、同步状态和异常。工作目录与备份盘都检查剩余空间。

建议把可用空间低于 20% 或不足容纳两份完整备份作为提醒线，按实际数据量调整。这是维护建议，并非程序内置告警。

### 4.2 每周

1. 抽查一份备份：文件齐全、能读取、容量没有异常下降；至少对比 state.json 和两个 SQLite 文件的哈希。
2. 在隔离目录做一次恢复抽查，步骤见第 7 节。核对配置、价格、图库、历史记录。
3. 查看云端备份任务最近一次成功时间、失败记录、存储容量及费用变化。没有权限时让云环境管理员出具结果。
4. 核对离职、调岗成员的访问权限；普通工作台账号与腾讯云管理员权限分别管理。
5. 整理旧备份，仅处理超过保留期且已有验证替代副本的文件；先放回收站，不能放入回收站时先告知负责人再安排。

### 4.3 每月，以及每次升级前

做一次完整恢复演练，记录花费时间；核对云端数据库、素材、账号、云函数是否都有可恢复资料。检查实际备份是否符合业务能接受的数据损失范围。

建议保留最近 14 份每日备份、最近 8 份每周备份、最近 6 份每月备份；每次升级前的备份至少保留到新版本稳定且完成一次恢复验证后。关键副本放在另一块磁盘或公司受控存储，同一硬盘的另一个文件夹不能抵御硬盘损坏。

## 5. 本机备份：按这个顺序操作

### 5.1 推荐办法：完整冷备份

“冷备份”就是先关程序再复制。下列操作对每台有本机草稿或本机 ERP 信息的电脑分别进行；只备份一台电脑不能覆盖其他人的未同步内容。

1. 在工作台正常保存。若同步正常，可先完成一次立即同步；若数据已经误删或存在故障，先保留现场，不为完成备份强行同步。
2. 在“多人同步 → 下载同步备份”保存额外一份 JSON。它是辅助资料，不替代完整 data。
3. 关闭工作台。打开任务管理器的“详细信息”，结合文件位置确认对应工作台进程已结束。不要结束所有 Python 或所有 WebView2 进程；其他程序也可能使用它们。
4. 建立新的备份文件夹，例如 `E:/工作台备份/电脑A/2026-09-20_1800_升级前/`，确保不是原 data 的内部目录。
5. 把整个 data 复制进去，结果应为“备份文件夹/data/state.json”，避免只复制其中几个文件。
6. 同时保留配套完整程序目录或对应版本的完整 ZIP。程序目录包含 EXE 和 `_internal`，不能只留下一个 EXE。
7. 填写备份记录：电脑、账号/工作区、版本、复制开始结束时间、源路径、备份路径、文件数、容量、待同步与冲突情况。
8. 打开备份目录检查文件，抽查哈希；重要备份再复制到独立介质。

复制报错、文件占用、空间不足时，这份备份标为“未完成”；排除问题后重新复制到新目录，不覆盖最后一份已验证备份。压缩可在复制完成后进行，压缩成功不等于业务恢复成功。

### 5.2 如何比较文件是否复制一致

在 PowerShell 7 中执行，先把路径替换成自己的真实路径。源目录仍须保持关闭、不再写入。这些命令只读取文件，不修改业务数据。

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath 'D:/实际程序目录/data/workspace.sqlite'
Get-FileHash -Algorithm SHA256 -LiteralPath 'E:/实际备份目录/data/workspace.sqlite'
```

两边 Hash 应完全相同。对 state.json、versions.sqlite 也可以同样核对。哈希相同只证明复制一致，不证明原数据库没有损坏；还需要恢复演练。

### 5.3 几种“备份”的区别

| 方式 | 适合用途 | 缺少什么 |
| --- | --- | --- |
| 本机历史版本 | 找回近期误改业务状态 | 原图字节、程序包、完整运行环境；历史还会清理 |
| 下载同步备份 JSON | 保存协作记录、草稿、游标、未确认提交供诊断或专门恢复 | 不含完整历史库、原图、密码，也不是全套本机 ERP 备份 |
| 退出后复制完整 data | 本机故障恢复、升级前保全 | 未缓存的云素材、其他电脑草稿、整个云环境 |
| 云数据库备份 | 云端数据故障恢复 | 本机未上传内容、素材对象、认证账号及云函数配置需分别确认 |

本机历史的当前规则是：相关历史操作触发检查，距离上次清理满 7 天后，删除超过 30 天的快照，但保留各范围的最新一份；界面每个范围最多列出最近 100 条。不是“永久保存所有版本”，也不是“数据库总共最多存 100 条”。

仓库中的云端历史迁移设计为展示最近 30 天提交，按周清理展示索引；实际是否已部署和定时任务是否运行，本次未核实。`wa_changes` 同步日志和 `wa_mutations` 提交回执不在这项清理范围内，不能照着 30 天规则手工删除。

## 6. 配置改错了：恢复业务历史

适用：软件可以正常使用，但配置、模板或人工价等被误改。只错一个字段时，先考虑按差异把那个字段改回；整份历史还原可能把同一时段其他正确修改也撤回。

1. 记下误操作发生时间、店铺、配置名称、操作人，通知同一工作区成员暂停相关编辑。
2. 暂停自动同步，等待当前同步结束；若有未确认提交或冲突，先保留现场并处理。暂停不会撤销已经上传的错误。
3. 按第 5 节备份当前现场。恢复后若发现选错时间，还能找回现在的内容。
4. 启动工作台，用原工作区成员登录，进入“多人同步 → 历史版本”。
5. 找到误操作之前的记录，点“查看差异”。逐条看当前值与还原后值，不只看时间。
6. 业务负责人核对影响后，点“备份当前并还原”。此操作生成新的业务版本；不是安装旧软件。
7. 抽查配置内容、人工价、模板、图片和本机库存信息。历史状态中的本机 ERP 信息也可能变旧，必要时重新读取公司 SQL、预览后应用。
8. 若需同步给其他人，先查看“修改与提交记录 → 本机 / 云端差异”，确认预期，再执行立即同步。先让一台其他电脑接收并检查，通过后恢复其他成员操作。

程序会阻止在同步运行、存在未确认提交或冲突时还原；当前数据变化会要求重新预览；库存来源不同也可能拒绝整库还原。遇到这些提示应处理原因，不手工改 SQLite 绕过检查。

不能把已经传播的错误靠“退出登录”撤回。恢复只在本机完成时，也不能宣称全员数据已恢复。

## 7. 电脑损坏或 data 损坏：恢复完整本机备份

### 7.1 先在隔离目录验证

1. 保留现有故障目录，完整复制或改名归档；不删除、不把旧备份直接覆盖进去。
2. 将与备份配套的完整程序包解压到一个新的可写目录，例如 `D:/工作台恢复验证/20260920/`。
3. 第一次启动前，把备份的整个 data 放到恢复目录的 EXE 旁。确认不是多套了一层 `data/data`。
4. 关闭原工作台。恢复演练电脑先断开网络，或由技术人员阻断测试进程外联；正式云端恢复演练需使用独立测试环境。仅暂停自动同步不等于完全隔离。
5. 核对启动环境没有把数据目录重定向回生产路径，再启动恢复目录中的 EXE。
6. 检查能否启动、配置数量及内容、人工价格、模板、可用图片、本机历史。没有网络或登录过期时，受登录保护的功能可能无法验证，登记为“待验证”，不为绕过限制直接接入正式云端。
7. 记录缺失图片、待上传数量、未确认提交、冲突及库检查结果。没有缓存的素材需后续在受控网络条件下从云存储验证。
8. 关闭恢复程序。正式切换前，由维护人员决定同步处理方案；不要把演练副本和原客户端同时连到正式工作区。

### 7.2 技术人员可选：检查备份中的 SQLite

在备份副本上用支持 SQLite 的工具以只读模式打开两个数据库，分别执行以下查询。普通使用者无需安装数据库工具；可让开发人员完成并记录结果。

```sql
PRAGMA quick_check;
```

应返回 `ok`。异常时保留该副本，换另一份备份验证并交给开发人员分析，不在唯一现场副本上做修复。即使返回 ok，也只是结构检查通过，仍需核对业务内容及图片。

### 7.3 正式恢复上线

先确认备份时刻到故障时刻之间可能丢失的修改，从其他电脑、云端和业务记录找补。恢复目录验证通过后再改启动快捷方式，原目录保留归档。

如果云端比备份更新，恢复本机不是把全员云端退回过去。旧备份带有历史游标、草稿和未确认提交，联网后可能拉取新数据或尝试提交旧请求。由开发人员检查队列与云端差异后决定接续原队列，或使用干净客户端接收云端，再迁移核准的本机内容。新手不要清空 outbox 或随意改游标。

跨电脑恢复可能需要重新登录工作台和重新填写 SQL 凭据。若选择空白客户端接收云端，原电脑独有的 ERP 信息、草稿、历史和生成图不会因此自动补齐，先保留原备份。

## 8. 软件升级：先把回退条件准备好

1. 留存当前完整程序包、版本号和完整 data 冷备份，登记云函数版本、迁移清单和工作区。
2. 向发布人员确认：这次是否改变数据格式、同步协议、云函数、数据库表或图片字段；上一版本能否读新数据。没有兼容性结论时按“尚未验证”处理。
3. 在新目录解压新版本，用 data 的复制品离线试启动；涉及同步的验收使用隔离测试环境。
4. 验证配置编辑保存、价格、图库、图片导出、历史预览；如果涉及云同步，再验证两客户端收发和冲突。
5. 安排正式切换时间，通知用户停改，完成最后一次现场备份后切换。新版本使用旧数据的副本，保留旧程序与升级前快照。
6. 同一台电脑只开一份正式工作台。启动快捷方式必须指向确定的正式目录。
7. 上线后抽查数据和同步，记录结果。旧程序、升级前备份及新版本产生的数据都保留到验收完成。

升级包中的 EXE 与 `_internal` 必须成套，不能只替换一个 EXE 或混用不同版本的依赖目录。分发给其他人的干净程序包不应含自己使用过的 data；不能直接把本机整个已用目录发给其他成员。

## 9. 软件版本要回退：先选对情形

| 情形 | 优先做法 | 主要影响 |
| --- | --- | --- |
| 业务内容填错，软件本身正常 | 第 6 节历史恢复或精确改回字段 | 恢复业务数据，会参与后续同步 |
| 新版界面或功能有问题，数据格式和云协议兼容 | 旧完整程序 + 当前 data 的副本，经验证后切换 | 尽量保留新版期间新增业务 |
| 新版改过数据格式，旧版不能读 | 旧完整程序 + 升级前备份，先隔离验证并制定增量补回方案 | 升级后的本机修改可能不在旧备份中 |
| 云函数发布引发问题，但数据库结构兼容 | 开发人员恢复兼容的旧云函数代码与配置 | 要验证所有仍在用的客户端 |
| 云数据库误改或迁移失败 | 第 10 节一致性恢复或修复 | 影响整个工作区甚至环境内其他工作区 |

### 9.1 只回退软件，尽量保留最新数据

1. 记录故障表现、新旧版本号和升级时间，暂停相关编辑及同步。
2. 关闭新版，备份当前完整 data。即使新版有问题，里面也可能有升级后的有效工作。
3. 获取上一版本的完整程序包，解压到新目录；不要覆盖新版原目录。
4. 复制当前 data 到旧版程序旁，在网络隔离下打开。绝不让旧版第一次试读发生在唯一生产 data 上。
5. 检查配置、价格、图库、字段、保存后重启及导出。若字段丢失、无法启动或格式异常，停止测试，保留错误，按不兼容处理。
6. 开发人员确认旧版与当前云函数、数据库、协议兼容，受控验证同步；离线打开成功不等于同步兼容。
7. 验收后切换正式快捷方式，确认全员使用约定版本，先一台受控同步，再另一台接收验证。

仅从版本号无法承诺 0.3.13 可以安全回到某个更早版本。必须验证目标版本；本次没有进行旧版本降级实测。

### 9.2 数据不兼容：回到升级前的程序与数据

1. 保留“升级前备份”和“故障时当前备份”两套，分别注明时刻。
2. 用旧完整程序加载升级前 data 的副本，离线验证。
3. 列出升级之后的新增、修改、删除以及尚未上传内容，确认哪些已在云端；制定逐项补回清单。
4. 业务负责人确认会暂时缺少哪些数据、如何补回，再安排正式切换。
5. 云端若仍有新版字段或更新记录，不能直接让旧客户端连接；开发人员先完成兼容修复、转换或明确的云端恢复方案。
6. 补回业务、两台客户端验证、记录损失范围后，再恢复全员工作。

“把旧 EXE 放回去”不能撤销 SQL 迁移；“把旧 data 覆盖回来”也不能撤销云端已经接收的修改。

## 10. 云数据库维护与恢复：管理员操作部分

### 10.1 平时应该检查什么

进入对应腾讯云 CloudBase 环境，先核对环境 ID 与程序使用的配置，再查看数据库、云函数、云存储和认证。不要仅凭相似的环境名称辨认正式环境。

正式业务链路为 `workbenchApi → wa_api → wa_*`。早期 `wb_*` 属于验证协议，不用它判断正式数据量。日常检查关注备份最近成功时间、数据库容量、连接或超时异常、云函数错误和素材读写失败，不直接修改业务记录。

| 对象 | 意义 | 操作边界 |
| --- | --- | --- |
| wa_workspaces | 工作区与同步头序号 | 不随意修改 head_seq |
| wa_members | 认证 UID 对应的工作区成员及启用状态 | 用户名不是 UID；开通认证账号后仍需正确成员关系 |
| wa_records | 当前业务记录 | 不直接改 data 绕过同步逻辑 |
| wa_changes | 同步重放日志 | 不因空间增长就清空或按展示期限裁剪 |
| wa_mutations | 已处理请求的回执，避免重试重复执行 | 不当作临时缓存删除 |
| wa_commit_history_index | 用户可见提交历史的索引 | 与同步日志区分；仅在对应迁移已部署时存在 |
| workbench-assets | 原始素材存储桶 | 数据库备份不等于素材备份 |

RLS 可理解为数据库的行级访问控制。账号不能访问时，先核对认证与成员关系，不通过关闭权限保护来排障。

### 10.2 可交给管理员的只读查询

在已核对环境的 PostgreSQL SQL 编辑器执行。把示例工作区 ID 换成准确值；本节不含写入 SQL。查询为空先核对权限和工作区，不立即断言数据丢失。

```sql
SELECT id, name, head_seq, created_at
FROM public.wa_workspaces ORDER BY created_at;

SELECT member_id, display_name, active
FROM public.wa_members
WHERE workspace_id = '替换为实际工作区ID';

SELECT entity_type, count(*) AS record_count, max(updated_at) AS latest_update
FROM public.wa_records
WHERE workspace_id = '替换为实际工作区ID'
GROUP BY entity_type ORDER BY entity_type;

SELECT seq, entity_type, entity_id, version, updated_at
FROM public.wa_changes
WHERE workspace_id = '替换为实际工作区ID'
ORDER BY seq DESC LIMIT 20;
```

记录数可能包含删除标记，不应直接等同于界面显示的配置数。最新提交时间可能采用 UTC，记录时转换为北京时间（UTC+8），避免选错恢复点。不要把成员信息、业务内容或连接信息贴到公共渠道。

### 10.3 云端备份必须向管理员问清楚

1. 当前环境的 PostgreSQL 服务支持哪些备份方式，是否已实际启用，最新成功备份是哪一份？
2. 能恢复到哪些具体时刻，保留多久；是否支持恢复到新实例或新环境？不能假定一定支持任意时间点恢复。
3. 备份是否包含表结构、数据、函数、触发器、权限和 RLS 策略？恢复工具版本与扩展是否兼容？
4. 原始素材的对象、路径、元信息和访问策略怎样备份？只有记录引用没有对象字节，图片仍可能丢失。
5. 认证账号、成员映射、云函数代码及环境配置如何保全？账号不能保证通过普通数据库备份还原。
6. 是否实际恢复过，验证结果和耗时在哪里？

这些问题的答案依赖实际服务和部署，本次未查询控制台。因此本文不编造“一键恢复”菜单或保证已有定时备份。首次接手应由云环境管理员补齐登记表后做一次隔离恢复演练。

### 10.4 云数据库出问题后的恢复顺序

1. 所有客户端停止编辑与同步，覆盖暂时离线的成员电脑；由管理员控制正式写入入口。单台暂停不能阻止其他电脑写入。
2. 先备份当前故障数据库、素材状态及各客户端 data，保存云函数日志、错误时间和发布记录。
3. 明确恢复范围：单个记录、单工作区，还是整环境。整库恢复可能同时影响其他工作区，不能默认只影响一个店铺。
4. 选择故障之前的备份点，优先恢复到隔离环境；记录备份时刻之后要补回的有效修改。
5. 成套检查工作区头序号、业务记录、变更日志、回执、成员、函数与权限。不能只恢复 wa_records 而保留另一时刻的日志与回执。
6. 配套恢复或核验素材对象及引用、认证映射、云函数版本和配置。
7. 在测试环境验证登录、初始化接收、两客户端同步、重复请求处理、冲突、图片与备份恢复；业务人员核对关键配置和价格。
8. 形成正式切换方案，明确损失窗口、补回清单、负责人与失败退路，再进行正式切换。
9. 旧客户端可能持有大于恢复点的游标及旧队列。先保留各机 data，再由开发人员决定重新初始化同步副本或迁移草稿，不能直接全员重连，也不能随意把游标改成 0。
10. 先开放一台受控客户端，第二台接收核验，通过后分批恢复全员使用并观察错误。

对于少量结构问题，开发人员可能选择追加修复迁移，保留新数据；对于严重损坏才选择一致性恢复。迁移目录没有可供新手无条件执行的通用反向回退脚本，不按文件日期倒序执行，也不重复跑全部初始化 SQL。

## 11. 常见问题处理表

| 现象 | 先查什么 | 下一步 |
| --- | --- | --- |
| 修改没有出现在同事电脑 | 本机是否保存、是否到同步时间、两端账号/工作区、待上传和错误 | 受控执行立即同步，再让对方接收；不要删 data |
| UNAUTHENTICATED / 登录失效 | 原账号、登录状态、环境 | 使用原账号重新登录，保留草稿 |
| NOT_MEMBER | 实际 UID、wa_members、active、工作区 | 交管理员核对成员关系 |
| UPGRADE_REQUIRED | 桌面与云端协议 | 获取兼容版本，不反复回退试碰 |
| 网络超时 / RETRYABLE / DATABASE_UNAVAILABLE | 网络、环境、云函数日志、结果待确认 | 保留原提交 ID 与队列，恢复后重试 |
| 库存没有变化 | 公司 SQL 更新时间、连接、预览是否已应用 | 走 ERP 流程；不把云同步当库存刷新 |
| 图片打不开 | 原图缓存、云对象、引用与访问权限 | 先核对素材，不只恢复数据库 |
| 启动后像新工作台 | EXE 与实际 data 路径、自定义环境变量 | 停止编辑，找回正确目录，不发布空数据 |
| 历史记录找不到 | 是否超过保留期、是否另一台电脑/工作区、列表最多 100 条 | 查完整备份；历史列表不是全员永久档案 |
| database is locked / 文件占用 | 同目录是否仍运行程序或恢复工具 | 正常关闭对应进程，再备份检查；不删除 WAL |
| 恢复后又出现新数据 | 是否连着比备份更新的云端 | 停止进一步同步，核查游标与差异，按第 7/10 节处理 |

### 12.2 什么时候才算完成

备份完成：退出后完整复制成功，文件可读、关键文件核对一致、版本与路径有记录。备份可恢复：另外完成隔离恢复与业务抽查。

本机恢复完成：正确版本与正确目录能启动，关键业务与图片核验完成，缺失与待补回内容有记录；网络或登录未验证的部分明确标注。

正式回退完成：旧版功能与数据兼容、正式云端兼容验证通过、至少两台客户端受控验证、快捷方式指向正确、升级后有效修改已补回或由业务明确确认处理办法。

云端恢复完成：数据库、日志回执、素材、账号映射、函数配置与客户端同步状态一致，全员恢复使用有分批验证记录。仅“页面能打开”不能作为恢复完成的证据。
