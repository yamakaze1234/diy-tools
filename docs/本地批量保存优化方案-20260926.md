# 本地批量保存优化方案

## 目标与交付边界

由 Astra 完成方案与验收，GPT-6 SOL（high）实施。先完成当前程序、数据、未提交源码备份，再修改代码。交付优化代码、独立候选版本、测试与性能报告。用户 2026-09-26 明确要求：完成后先不安装新版；不得覆盖当前安装目录、迁移当前业务数据、修改桌面快捷方式或替换正在运行的旧版。用户可在开发期间继续使用旧版。候选测试禁止生产云端写入及 ERP 写入，不提交或推送 Git。

## 已有证据

当前版为 v1.0.22，已经包含网页同步时间戳冲突修复及 WPS 特殊配件自动识别。两项修复必须保留。

隔离副本实测：716 条配置（354 条有效）、3,574 条输出源、12,741 条成本源；批量改同一链接 32 套配置，请求 61.38 MiB，后端保存 16.95 秒。changesBetween 调用两次合计 5.67 秒，applyWorkspace 3.08 秒，initializeMaterializedState 1.10 秒，normalizeWorkspaceState 1.74 秒；历史保存两次合计 0.75 秒。上述计时包含嵌套调用，不可相加为总时间。旧计时报告仅用于定位，最终比较必须在相同备份、操作、环境下重测。

瓶颈链路：浏览器克隆全工作区及编辑基线 → 全量 POST /api/state → Python/QuickJS 多次全量 JSON 往返与差异计算 → 全 records 物化 → 全量状态返回 → 浏览器全量回执合并 → 全部链接商品文件重写。图片在保存后延时处理，但批量实际配件修改也可能使不相关图片入队。

## 必须完成的五项优化

### 1. 只计算一次可复用的差异

将保存准备中的规范化、验证、投影、差异与活动构造形成明确结果，由日志和持久化共用。相同基线不能在 Service.update_state 与 Cloud.persist 重复计算全量 changesBetween。基线被并发合并或旧记录兼容逻辑调整时必须重新准备，不能把过期差异当缓存复用。原有全量 /api/state 路径保留兼容并获得可复用差异优化。

### 2. 减少 Python 与 QuickJS 往返

纯规则侧增加保存准备／批量记录校验等组合函数，将连续规则调用合并；批量保存仅传受影响配置和必需的相关成本/输出源上下文。批量记录的合并与校验一次过桥，不逐条往返大对象；合并物化与默认字段初始化。复用既有验证和 mergeWorkspaceEdit，不另造弱化的校验器。不得用长寿命缓存持有过时成本、版本或店铺信息。

### 3. 批量修改专用增量保存接口

新增本地 API（推荐 POST /api/configs/batch），只接收已有目标配置的 ID、编辑基线、修改后配置及操作说明，携带工作区 revision 和必要操作标识。明确 payload/数量上限、ID 唯一性与现存记录要求，验证登录、请求来源、店铺及内容；未包含的记录绝不是删除。支持本链接/勾选跨链接范围，以及展示 parts、实际 actualParts 单独或同时修改，人工 addons 行为沿用现有契约。

服务端持有现有工作区写锁，校验全部条目后在一个 SQLite 事务更新目标草稿、工作区恢复快照和本地审计。任一失败，整个批次不产生部分业务写入。保留修改前历史备份、成功后历史版本。不能靠跳过冲突或备份提速。

前端先处理已有未保存内容，预览与提交之间重新检查范围和来源，应用过程中禁用重复提交。成功回执只带已保存目标配置、revision、时间及必要日志/失效信息。将回执合并到 acceptedState 和当前状态，保留请求期间后续输入与撤销能力。错误保留草稿，不能显示已保存。

并发策略必须明确：目标同字段变更、删除/恢复冲突保持拦截；不相关字段不丢失。若后台全局 revision 已变化而回执无法覆盖其他配置，走既有全量重基/刷新回退，不能只递增 acceptedState.revision 后假装已接收其他配置。网络回执丢失后的重试必须幂等，不重复加数量、重复历史或悄悄覆盖。旧 Node 原型后端不支持新接口时需能力检测或明确兼容回退，不把 409 当作可绕过的失败重试。

### 4. 局部物化与派生文件增量更新

只重新构造受影响配置，复用未变集合；传给规则层的成本/来源上下文按目标 goodsId/sourceId 收集。删除、旧配置缺 actualParts、缺 lineId、排序字段、共享成本派生字段以及特殊配件都遵循现有规则。不以省事为由重写未选择的展示或实际清单。

现有全量 workspaceState 恢复快照可继续一次持久化，以维持崩溃恢复契约；它不是理由去多次编码/物化整个工作区。state.json 与 SQLite 的一致性沿用明确的主数据优先级，并测试写入失败和重启恢复，不得宣称跨文件原子事务。

products-standard 只重新计算/写入受影响的店铺/链接；同内容文件不替换。链接移动、删除、共享设置或成本变动必须准确扩大失效范围。索引与内容保持一致；全量导入/云接收/恢复保留全量重建入口。业务保存成功与派生文件失败不得混淆，必要时给出可重建状态，不能静默返回不一致成功。不要改变外部商品 JSON 契约。

### 5. 图片队列按展示变化失效

保持保存后再生成图片，按配置 ID 去重，跳过只改 actualParts/核算字段的配置。仅可见展示内容、布局或素材变化才标记图片过期；若选择实际配置但变动会影响海报显示价格等内容，按真实海报输入判断。输入和新保存优先，旧 revision 图片不能覆盖新图；导出仍等待对应正确版本。保留现有失败提示与手动重试。不要在“应用修改”主路径同步生成一批海报。

## 验证与接受条件

1. 回归：相关 JS、Python 单元和集成测试；WebView2 实际窗口点击批量预览、应用、刷新，分别只展示、只实际、同时修改，验证未选范围完全不变。
2. 数据保护：多记录事务中途故障回滚、过期计划、同字段并发、无关字段/无关配置并发、远端删除、本地新增/旧记录缺字段、幂等重试、非登录、异常 ID、重复 ID、无变化保存、异常退出后恢复、历史还原/撤销。
3. 派生结果：只写受影响商品，未变文件内容与修改时间不变；移动/删除/恢复的索引正确；共享成本、特殊配件、税价不被旧缓存覆盖；旧网页冲突和 WPS 自动识别回归通过。
4. 图片：实际配置单独更改不会生成无关图片，展示变化正确入队，新旧 revision 竞态不会错误覆盖，显式导出可用。
5. 性能：从同一不可变备份创建旧、新两个独立数据副本；禁止使用继续变动的生产数据作为前后样本。固定同一链接 32 套配置相同修改，测请求/响应大小、后端总耗时、规则过桥次数与耗时；另测真实窗口点击应用至保存完成。主目标是该批次请求至少减少 80%、后端中位耗时至少减少 50%；这些是验收目标，非预先承诺。如未达到，解释瓶颈并继续优化，不用小样本冒充真实数据速度。
6. 独立审查：针对本任务实际差异检查并发、事务、回执、增量失效、数据恢复。核实问题再修复，修复后复跑受影响检查。
7. 候选交付：独立目录构建，保留正确版本/构建标识；只做隔离启动与必要 UI 检查。候选无真实业务数据、凭据及登录缓存；不触碰当前安装与快捷方式。结果中写清源码测试、隔离运行、真实云/ERP未写入的证据边界。

## 用户追加需求（同一候选版交付）

1. “复制一份配置”紧跟原配置插入，而不是追加到列表末尾。持久化 workspaceOrder，在保存、重新载入和同步投影后保持位置；普通情况只给新配置分配中间排序值，历史记录缺排序或浮点间隔耗尽时只修复当前链接，其他链接不重排。覆盖末项复制、连续复制、旧记录及同步乱序返回。
2. 勾选导出恰好一张时直接下载 PNG，文件内容验证为 PNG；多张桌面导出按第 4 项改为文件夹，普通浏览器保持 ZIP 与清单。当前单张导出按钮本来已为 PNG，修复批量入口仅选一张仍打包的情况。导出仍采用点击时快照，不等待尚未完成的本机保存；生成失败不产出空压缩包。
3. 新建配置默认独立、未绑定链接，不跟随当前勾选或打开的链接；保留店铺上下文，但不继承该链接的机箱图片和图集。归入链接由用户主动选择。复制配置仍保留原配置归属，紧跟原配置插入。验收覆盖当前链接含多张机箱图片、误勾选其他链接、新建保存重载及主动归入链接。
4. 桌面版多张导出选择文件夹，创建带时间的新子文件夹，写入编号 PNG 和导出清单，不覆盖已有导出。单张仍直接 PNG；普通浏览器无桌面接口时保持 ZIP 兼容。取消选择不写文件；全量生成失败不导出空包，部分失败在界面及清单说明。验证原生桥接落盘、PNG 格式、清单、重名不覆盖、登录过期、路径校验及取消。
