# 部署与开发

## 直接下载程序

在 [GitHub Releases](https://github.com/yamakaze1234/diy-tools/releases) 下载 Windows ZIP，完整解压，保留 EXE 和 `_internal` 同级。运行不需要另装 Python 或 Node，需要 Windows 10/11 x64 和 WebView2。

公开包使用占位云配置。管理员完成下述云部署后，编辑程序目录中的 `_internal/web/.env.local`，填入自己的客户端配置，再启动 EXE。包内没有现有团队账号或生产数据，不能直接登录原团队。若缺少 WebView2，运行包内微软引导安装程序，安装时需要联网。

## 源码环境

准备 PowerShell 7、Git、Node.js 24、uv 和 WebView2。Python 使用 `.python-version` 指定的 3.13.6；依赖以 `pyproject.toml` 和 `uv.lock` 为准，支持 Windows x64。

```powershell
git clone https://gitea.cq360.top/CoreStudio/diy-tools.git
Set-Location diy-tools
npm ci --prefix prototype
uv sync --project python-desktop --locked
if (!(Test-Path prototype/.env.local)) { Copy-Item prototype/.env.example prototype/.env.local }
```

## 云环境与成员

准备自有 CloudBase 环境，启用用户名/密码认证、PostgreSQL、云函数及存储。迁移依赖平台的 `auth.uid()`、`auth.role()`、`auth.jwt()`、`storage.buckets` 和 `storage.objects`，不能直接在普通空 PostgreSQL 上运行。

按文件名顺序审阅并执行 [迁移目录](../cloudbase/migrations/) 的 SQL 文件，包含基础验证表、身份校验、应用协议 2、图片成员权限、基线保护及后续历史记录维护迁移。它们不是可无限重复执行的幂等脚本；已有环境先核对已执行版本。应用迁移创建 `workbench-main` 工作区，但不会自动开通认证账号。

将 [workbenchApi](../cloud/functions/workbenchApi/) 部署为同名云函数，运行时须支持全局 `fetch` 和 `AbortSignal.timeout`，设置 `WORKBENCH_ENV_ID` 为自己的环境 ID。检查客户端入口 `https://<envId>.api.tcloudbasegateway.com/v1/functions/workbenchApi` 可达。协议 2 转交 `wa_api`；`wb_api` 属于早期验证结构。图片桶为 `workbench-assets`，保留迁移定义的成员访问策略。

在认证系统创建账号后，精确复制认证 UID，在 `public.wa_members` 添加 `uid`、`workspace_id`、唯一稳定的 `member_id`、`display_name`、`active=true`。工作区必须存在。只有认证账号而没有有效成员记录时无法进入业务工作区。

当前应用没有成员角色字段；有效成员业务能力相同。云控制台管理权限与业务成员资格分开。成员改名仅更新显示名，停用可设置 `active=false`；这不会擦除对方电脑已保存的数据。实际认证控制台入口以所用环境为准。

## 客户端配置

编辑 `prototype/.env.local`，保持 `CLOUDBASE_PUBLIC_CONFIG=` 后面为单行 JSON。

| 字段 | 内容 |
| --- | --- |
| envId | 自有 CloudBase 环境 ID |
| region | 环境地域 |
| functionName | workbenchApi |
| accessKey | 供客户端 SDK 使用的公开访问键，不能填云管理员 SecretKey |

客户端配置会进入分发资源，只能使用可给客户端分发的参数。环境 ID、工作区 ID 和认证 UID 不同。`cloud/config.example.json` 仅供部署参考，Python 实际读取 Web 资源中的 `.env.local`。

```powershell
npm run build:sync --prefix prototype
node python-desktop/build-web.mjs
Copy-Item prototype/.env.local python-desktop/web/.env.local
uv run --project python-desktop --locked python -X utf8 python-desktop/main.py
```

修改前端后重新运行 Web 构建。它复制前端及资源、打包 QuickJS 规则，生成空白业务种子，并将云配置重置为公开示例；本机开发需要再次执行上面的配置复制命令。分发构建保持公开示例配置。首次登录后按使用手册发布本机数据或接收已有工作区。

## 隔离开发

```powershell
$env:DIY_WORKBENCH_DATA_DIR = Join-Path (Get-Location) '.verification/dev-data'
$env:DIY_WORKBENCH_USER_DATA = Join-Path (Get-Location) '.verification/dev-runtime'
uv run --project python-desktop --locked python -X utf8 python-desktop/main.py --port 0
```

变量作用于当前终端及子进程；显式设置后不自动迁入旧 AppData 数据。`--port 0` 分配空闲端口；默认使用 4179 或上次记录的端口。添加 `--headless` 仅启动后端并输出 `WORKBENCH_READY`，不会绕过登录。

首次启动 Node 开发服务前，按[仓库说明](../仓库说明.md)从示例生成缺失的 seed/catalog 文件，已有文件保持原样。Node 原型使用 `npm start --prefix prototype`，默认端口 4178，默认数据目录 `prototype/.local`，隔离变量是 `DATA_DIR`，不是 Python 的变量。

## ERP 适配

[sql_service.py](../python-desktop/sql_service.py) 只读查询 SQL Server 的 `[库存].[分库库存]` 和 `[库存].[库存查询]`。前者需要 goods_id、库房、商品编码、商品名称、分库数、分库可销数、分库待入和库存成本；后者提供完整商品目录。查询包含 `TOP (100001)` 限制及后续校验。

默认端口 1433。按商品 ID 精确匹配，以公司大库“分库可销数”为库存、“库存成本”为单件 ERP 成本。其他 ERP 先适配并验证字段，不只替换连接地址。账号密码在应用内填写，读取后预览确认才应用。

## 测试与打包

```powershell
npm test --prefix prototype
uv run --project python-desktop --locked python -X utf8 -m unittest discover -s python-desktop/tests -v
uv run --project python-desktop --locked python -X utf8 python-desktop/build.py
```

先完成 Web 构建再跑 Python 测试。默认 Node 入口运行全部 `tests/*.test.mjs`，使用随源码提供的合成数据，无需私有业务样本。浏览器、在线云同步和打包验收脚本需要额外环境，不在默认命令内。

构建结果位于 `release/python-<版本>-<时间>/`，路径记录在 `python-desktop/verification/latest-build.json`。将官方 `MicrosoftEdgeWebview2Setup.exe` 放到生成的应用目录后运行：

```powershell
uv run --project python-desktop --locked python -X utf8 python-desktop/package.py
```

脚本收录 EXE、_internal、使用说明和引导安装程序，生成 SHA256 清单与 ZIP，排除程序旁 data。同版本 ZIP 已存在会停止；保留旧包或移至另一目录后再生成。

## 部署验收

在隔离工作区验证：成员身份正确；首次发布或接收成功；两个客户端能传递一次修改并处理冲突；图片可上传下载；ERP 确认前不改变业务数据；重启后本机状态保留。单元测试通过不代表云环境部署完成。
